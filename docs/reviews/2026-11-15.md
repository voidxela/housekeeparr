## Findings

### R1 — High: malformed or incomplete listings become authoritative absence

Locations: `internal/adapter/arr/arr.go:125–166`, `internal/adapter/transmission/transmission.go:225–240`.

With HTTP 200 and JSON content type, the shared arr queue accepts `{}` and `null` as complete empty queues. It also accepts `{"totalRecords":2,"records":[{"id":1}]}` as complete with the default page size, because a short page breaks the loop without checking the expected count. Transmission accepts `{"result":"success","arguments":{}}` as a complete empty transfer list.

All four cases were reproduced with temporary Go overlay tests. Downstream snapshot persistence interprets complete-list absence as disappearance; this can remove relationships and resolve existing findings without authoritative evidence. It violates §§3.2–3.3 and 4.

Require valid response envelopes and mandatory list/count fields, distinguish explicit empty lists from missing/null data according to verified upstream contracts, validate counts, and mark truncated listings incomplete. Audit equivalent client and health readers. Add adapter tests plus engine/store tests proving these responses cannot remove existing entities or resolve findings. A legitimate empty complete list must still work.

### R2 — Medium: a recheck counter increase resolves a stall

Location: `internal/engine/resolution.go:49–58`.

`decideStall` compares bytes before considering checking state or assessment validity. Reproduction using `stalledSetup`: set the existing stalled transfer to `StateChecking`/`checkingDL`, increase `VerifiedBytes` from 2 GiB to 3 GiB, retain wanted bytes, and poll once. The finding resolves during checking. Existing tests check checking-state and counter-change cases separately.

Require compatible, trustworthy progress evidence before resolution; preserve the finding while checking and establish an appropriate baseline after recheck. Test checking with increasing counters, subsequent resumed downloading, and genuine progress beyond the applicable baseline. Do not suppress legitimate progress merely because a transfer was previously paused.

### R3 — Medium: unknown states count as verified error recovery

Location: `internal/engine/resolution.go:114–133`.

`consecutiveNonErrors` accepts every state except `StateError`, including `StateUnknown`. Reproduction: establish a client-error finding with two error samples; then provide two `StateUnknown`/`futureState` samples. The finding resolves with a verified-recovery explanation.

Use positive supported evidence of error clearance. Unknown/missing/unsupported state must keep the finding open with an explanation. Test unknown transitions and genuine recovery; consider evidence freshness and gaps explicitly.

### R4 — Medium: missing Transmission metadata evidence is assumed true

Location: `internal/adapter/transmission/transmission.go:257` and dependent progress/privacy mapping.

`hasMeta := r.MetadataPercent == nil || *r.MetadataPercent >= 1` treats missing `metadataPercentComplete` as acquired metadata. A synthetic response with downloading status, wanted/remaining sizes, `isPrivate:false`, and no metadata percentage becomes known-public. This was reproduced directly through normalization. It also permits metadata-dependent progress and completion interpretations.

Represent absent metadata evidence as unknown or reject the incompatible response; do not silently establish privacy or recovery prerequisites from it. Test absent/null/invalid metadata fields and explicit known metadata states. No write path currently exploits this, but it is a blocker before adding one.

## Race detector investigation

`go test -race ./...` fails before application tests with:

```text
FATAL: ThreadSanitizer: unsupported VMA range
FATAL: Found 39 - Supported 48
```

Process mappings are in a 39-bit range. A non-destructive `mmap` probe with `MAP_FIXED_NOREPLACE`, one page and no access, succeeded at `1<<36` and failed with ENOMEM at `1<<46`. This supports an address-space limit rather than ordinary RAM exhaustion. Current upstream LLVM's Go-specific ARM64 mapping supports 47/48-bit layouts, not 39-bit; C/C++ TSan's separate 39-bit support does not fix Go's runtime.

There is no supported in-session native fix through project code or system package installation on this running kernel. A compatible host/VM/kernel or native amd64 CI runner is the practical next step. Docker on the same kernel does not change this limit. Do not disable race instrumentation, patch out the runtime guard, or change host-wide ASLR settings and claim coverage. Cross-architecture emulation was not attempted and is not a validated workaround. No system packages or kernel settings were changed.

Sources: [Go issue 29948](https://github.com/golang/go/issues/29948), [upstream Go ARM64 TSan mapping](https://github.com/llvm/llvm-project/blob/main/compiler-rt/lib/tsan/rtl/tsan_platform.h) (`MappingGoAarch64`). These explain the diagnosis; the failure above is from this machine's installed toolchain.

## Transmission direction and documentation corrections

The user's minimum target is both Transmission 4.0.x and 4.1.x. [Released 4.1.4 RPC documentation](https://github.com/transmission/transmission/blob/4.1.4/docs/rpc-spec.md) explicitly retains the legacy protocol throughout Transmission 4, while deprecating it. Separate implementations are therefore not justified solely by deprecation. Start by validating the existing protocol against pinned 4.0.x and 4.1.x releases, for observation and later each required write workflow. Introduce a second protocol only when concrete compatibility or capability evidence requires it; retain 4.0 support. Future removal remains a documented limitation, not a reason to silently drop 4.0.

Correct stale prose during implementation: SPEC's opening says nothing is implemented; compatibility legend still says no integration runs exist; STATUS's remaining section incorrectly says none of the six adapters have real validation. STATUS currently lists JSON-RPC 2.0 as mandatory remaining work; replace that with the evidence-driven 4.0/4.1 compatibility requirement above. Do not imply fixtures establish every version between a floor and current releases.
