## R5 — High: live safety checks are incomplete and only precede the first write

Locations: `internal/action/action.go:248,327`,
`internal/action/plan.go:264–280`, `internal/workflow/recovery.go:148–176`.

The fingerprint contains transfer presence, class, verified bytes, manager ID,
queue ID and download ID. Live refetch does not compare privacy, content IDs,
category/file selection, monitoring or manager health, and only reads the
selected manager's queue. The recovery Manager interface cannot read content
monitoring or health. Local planning has no corresponding live safety gates.
A privacy or ownership change can therefore leave a proposal executable.
Other-manager associations arising since the last engine cycle are not checked.

`Execute` calls Refetch once. `run` journals and dispatches subsequent steps
without another decision-relevant read or gate check. The first step's
postcondition reads the queue/blocklist/history, not the transfer's continued
eligibility. Progress, completion or policy/stop changes between manager failure
and client stop need a fresh assessment. SPEC §§7.1 and 10 require fresh checks
before each consequential write, not merely before the workflow.

Reproduced with temporary Go overlay tests: changing public → private and
changing episode/series IDs leaves the fingerprint identical; changing the
executor's fingerprint after the first write still dispatches `client.stop`
and reports success. Revalidation must be step-specific: after the first step,
queue disappearance is expected and must not be compared blindly with the
original fingerprint. Recheck current version/capability, policy and affected
ownership/health scopes; journal divergence and hold partial work without replay.
Add focused tests for changed privacy, monitoring, content, progress/completion,
new shared ownership and pause/emergency stop between steps.

## R6 — High: content locks, budgets and overrides use release-attempt identity

Locations: `internal/store/queue.go:48–63`,
`internal/action/plan.go:123,248–252`, `internal/app/actions.go:110,135–146`.

`QueueItemKey` includes DownloadID. The planner uses that key as content lock
and per-content budget scope; the app also uses it as the content override
identity. Two releases for the same episode/movie consequently get different
content locks and allowances. The advertised three-per-item retry protection
resets with each replacement; concurrent workflows for different transfers of
the same content do not share the intended content lock. Content exclusions
and overrides also fail to follow replacement attempts.

Reproduced with a planner overlay test: episode 1 on releases aa and bb uses
`content:sonarr|aa|episode:1` and `content:sonarr|bb|episode:1` for both locks
and budget scopes. Introduce manager-instance + stable content identity,
separate from queue/release-attempt identity. Define pack/multi-episode scope
explicitly. Preserve prior durable history through a forward migration where
needed; do not edit committed migrations. Preview currently checks only the
transfer lock/cooldown; include every affected content lock/cooldown as well.

## R7 — Medium: budget enforcement is hidden and lacks specified exhaustion semantics

Locations: `internal/action/plan.go:246–252`,
`internal/action/action.go:268–275`, `internal/app/actions.go:63–163`.

The planner hard-codes 20 acquisitions per aligned 24-hour window globally,
three per aligned seven-day window for its purported content scope, and a
24-hour success cooldown. These numbers are implementation proposals, not
approved SPEC defaults. Windows use `time.Truncate`, not rolling last-day/week
counts or necessarily the operator's local calendar. Reservations are consumed
before dispatch and remain consumed on definite refusal or pre-dispatch
cancellation. No configuration or targeted budget reset is implemented.

Preview does not read budget usage, so it can advertise eligibility only for
execution to reject the action. Exhaustion is an execution error rather than a
persistent finding with the used/limit, affected scope, next eligibility and
corrective control. At the next aligned window the allowance returns without
the per-item intervention/review semantics described in SPEC §7.

Keep bounded acquisition and retry control, but separate fleet pacing from
repeated unsuccessful attempts for one content item. Make limits/windows and
cooldowns configurable with provenance and visible in CLI/web previews; count
manager-native replacement requests too, while disclosing their unbounded
upstream fan-out. Define reservation release for provably unsent requests;
never refund an uncertain external request as if it had not happened. Keep
findings visible while deferred and schedule fairly when capacity returns.
Per-item repeated-failure intervention and global rate deferral need distinct
explanations. Numeric defaults and any change from §7's review/reset requirement
remain product proposals, not approval inferred from this review.

## Disposition of Claude's five decisions

1. **Manual actions and modes.** Refusing operational writes in observe is
   required by SPEC §6. Paused explicitly stops automation, so deliberate
   confirmed manual actions there are a reasonable interpretation. Workflow
   toggles are described as *automation* permissions; permitting a deliberate
   one-off manual action while automation is disabled is reasonable, but should
   be documented and clearly previewed. This is a review recommendation, not a
   new user-approved amendment. Distinguish disabled automation from a workflow
   pause, exclusion or global emergency stop; manual must honor hard safety
   restrictions, all affected scopes and acquisition limits. Test a mode ×
   origin × permission/exclusion/emergency-stop matrix. Do not add another
   confirmation round for each implementation step.
2. **Registering real writes.** Consistent with the approved implementation
   direction and recorded disposable-instance evidence; no blanket reason to
   unregister solely because writes now exist. Exact-version gating and
   explicit confirmation are appropriate. Registration is not proof that all
   runtime safety conditions are checked: R5/R6 apply to existing manual writes,
   and should be corrected before expansion. Describe this as a tested manual
   execution sequence, not a complete operational recovery workflow.
3. **Blocklist matching without hashes.** Composite evidence is appropriate
   when released APIs lack identity, but title/time alone is insufficient
   (SPEC §3.1). The executor combines queue absence, history by download ID and
   blocklist evidence, which is stronger. Still, Blocklisted uses EqualFold
   rather than byte-exact title matching, permits entries five minutes before
   dispatch and has no pre-action baseline/unique match check; HistoryEvents
   discards timestamps and event IDs. An old failure plus an existing matching
   entry can be mistaken for this action. Capture baseline IDs and verify a new
   content-scoped event/entry where supported; test title collisions, stale
   history and concurrent manual activity. Keep ambiguity uncertain. Product
   explanations must say matching release evidence, not guaranteed hash-only
   identity or expiry. Do not broaden blocklist deletion/reconsideration scope.
4. **Retry after definite failure/cancellation.** Correct for requests proven
   unsent/refused with no earlier side effects, after fresh re-planning and
   cooldown/budget checks. Preserve every intent. An accepted request whose
   effect is not yet visible does not prove that it will never take effect:
   `settle` currently classifies NotHolds + no dispatch error as failed. Audit
   that branch and endpoint-specific refusal classification before relying on
   the newly reusable failed key; use uncertain for delayed/partial effects.
   Operator review does not itself prove an acquisition was unsent. Test a
   late effect after the observation deadline and review-to-failed followed
   by another manual action. No automatic blind retry of acquisition writes.
5. **Hard-coded recovery budgets.** The need is approved (§§7, 9.1, 10); the
   particular limits are not. They prevent loops and a mass recovery burst
   after an outage, but a small fleet-wide quota can indeed defer healthy
   unrelated work. Correct R6/R7 and show deferral/intervention explicitly.
   Never silently abandon findings or claim budget exhaustion proves no release
   exists. A paced queue plus scoped repeated-failure control is preferable to
   treating 20/day as a universal product rule. Removing all bounds would
   contradict the approved spec; changing that requirement needs an explicit
   product decision.
