## 1. Summary Verdict

**Verdict: Keep trialling; do not cut a v1 release yet.**

The core safety architecture is sound and safe to continue running in the production trial with monitoring:

- **No unjournaled write path was found.** Every external write flows through `action.Coordinator.Execute` (`internal/action/action.go:255-395`), which transactionally writes `action_intents`, `action_steps`, `action_locks`, and `action_attempts` (and updates `journal.hwm`) before `BeginStep` (`dispatching` + baseline) and `Dispatch`.
- **No blind retry of uncertain acquisitions was found.** Timeouts, HTTP 408, malformed 2xx responses, and accepted-but-unobserved writes transition to `IntentUncertain`, retain their locks and budget reservations, open scoped breakers, and are never re-dispatched by `Reconcile` or subsequent cycles.
- **No content deletion or move path exists.** All four `arr.RemoveFlags` are always explicitly sent, `removeFromClient=false` is enforced before dispatch (`internal/workflow/recovery.go:127`, `internal/workflow/pack.go:167`), and client stops invoke only data-retaining stop/pause RPCs (`torrents/stop|pause`, `torrent-stop`, `core.pause_torrent`, `d.stop`).
- **No race exists across 5 actions per cycle.** `DispatchAutomatic`, `DispatchSearches`, and manual `Act` share `Service.execMu` (`internal/app/dispatch.go:62`, `internal/app/actions.go:173`, `internal/app/searches.go:163`), and each candidate in a pass re-runs `Preview` after the prior action's transaction commits its budget reservations and retained records.

However, **five High-severity and ten Medium-severity confirmed defects** block release readiness. The top risks are:

1. **Silent unauthenticated remote exposure on loopback + `trusted_proxy = true` (H1):** The exact shared-host reverse-proxy setup documented in `packaging/README.md` bypasses the `web.password` requirement if `web.password` is omitted, because validation only enforces auth on non-loopback `web.listen`.
2. **Web UI and every finding falsely claim `Observe-only` and `"Automatic recovery is not implemented in this release"` in `automatic` mode (H2):** Operators looking at the web UI or CLI findings are told nothing will change while automation is actively executing.
3. **Cooldown monotonicity inversion for `success_cooldown = "0s"` (H3):** `ActiveCooldowns` treats `limit == 0` as "keep recorded 24h end" instead of "0s cooldown", so disabling cooldowns keeps old cooldowns active longer than setting `"1s"`.
4. **Unbounded `action_attempts` table growth under the new default rolling 24h attempt window (H5):** `pruneAttempts` only prunes `attempts:%` rows predating a manual reset in `action_budget_resets`; with rolling windows, operators never reset, so attempt rows accumulate forever and eventually truncate `AttemptSummaries` (`LIMIT 500`).
5. **Broken `base_path` navigation (`downloads.html`), `guard()` ordering, and reverse-proxy port mismatch (H4, M3, M4):** One link omits `{{base}}`, bare `base_path` / out-of-prefix requests bypass Host validation and security headers, and documented `proxy_set_header Host $host` breaks all POSTs on non-standard HTTPS ports.
6. **Correlated-stall hold freshness/completeness gaps, probe starvation on failed/cancelled/pack intents, and `maxLiveEvaluations` starvation at `actions_per_cycle = 5` (M1, M2, M6).**

##### H1 — `trusted_proxy = true` on loopback allows unauthenticated remote web exposure
- **Location:** `internal/config/config.go:721-730`, `internal/web/server.go:62-77`
- **Defect:** Both config validation and `web.New` enforce `web.password` and `web.allowed_hosts` only inside `if !isLoopbackHost(host)`. When an operator sets `listen = "127.0.0.1:8484"` with `trusted_proxy = true` (and/or `base_path = "/housekeeparr"`), which is the exact shared-host topology documented in `packaging/README.md:73-86`, omitting `web.password` is silently accepted.
- **Concrete failure scenario:** Operator configures `[web]` with `listen = "127.0.0.1:8484"`, `trusted_proxy = true`, `base_path = "/housekeeparr"`, `allowed_hosts = ["box.example"]`, and omits (or comments out) `password`. `housekeeparr config validate` exits 0 and `housekeeparr run` starts serving without authentication behind nginx. Anyone reaching `https://box.example/housekeeparr/` can read findings, pause/resume workflows, reset attempts, and trigger manual actions. Directly violates SPEC §2.2 and §12 ("Remote unauthenticated access must not be enabled accidentally").
- **How verified:** Code path traced (`config.go:721-731`, `server.go:62-77`, `packaging/README.md:73-86`).
- **Suggested fix:** Require `web.password` and `web.allowed_hosts` whenever `!isLoopbackHost(host) || w.TrustedProxy || w.TLSCert != ""`. Keep `web.New` enforcing the same invariant so callers cannot construct an unauthenticated proxied server.

##### H3 — `ActiveCooldowns` treats `success_cooldown = "0s"` as "keep full recorded cooldown" instead of "no cooldown"
- **Location:** `internal/store/actions.go:549-555`, `internal/app/actions.go:137`, `internal/app/searches.go:93,466`
- **Defect:** `config.go:258` explicitly allows `success_cooldown = "0s"` (`if l.SuccessCooldown < 0 || ...`). However, `ActiveCooldowns(ctx, now, limit)` uses `limit == 0` as a sentinel meaning "do not cap by `since + limit`; keep the stored `until`". Every caller passes `s.cfg.Limits().SuccessCooldown` directly.
- **Concrete failure scenario:** A recovery ran when `success_cooldown = "24h"`, recording `until = T + 24h`. One hour later, the operator sets `success_cooldown = "0s"` to disable cooldowns so stalled replacements recover immediately. `ActiveCooldowns(ctx, T+1h, 0)` runs `SELECT ... WHERE until > ?`, keeping the 24h cooldown active for another 23 hours! Setting `success_cooldown = "1s"` expires it immediately, whereas `"0s"` holds it for 23 hours.
- **How verified:** Code path traced (`config.go:258`, `store/actions.go:549-555`, `app/actions.go:137`, `app/searches.go:93,466`, `handled_migration_test.go:493-496`).

##### H5 — `action_attempts` rows for `attempts:%` are never pruned under the default rolling 24h attempt window
- **Location:** `internal/store/retention.go:110-116`, `internal/app/actions.go:344`
- **Defect:** `pruneAttempts` deletes `attempts:%` rows only when `at < ? AND at < (SELECT max(r.at) FROM action_budget_resets r WHERE r.scope = action_attempts.scope)`. Commit `2a61ae4` made `content_attempt_window = "24h"` the default so attempts roll off automatically without manual resets. When a scope has no row in `action_budget_resets`, the subquery returns `NULL`, `at < NULL` evaluates to UNKNOWN, and **no `attempts:%` row is ever deleted**.
- **Concrete failure scenario:** Over months of automatic recovery under default settings, `action_attempts` grows without bound (violating SPEC §10 bounded retention). Once more than 500 `attempts:%` rows exist, `Service.AttemptSummaries` (`internal/app/actions.go:344`, `s.st.Attempts(ctx, "attempts:", 500)`) silently drops older scopes if they appear beyond row 500, and SQLite scans grow linearly.
- **How verified:** Code path traced (`retention.go:110-116`, `config.go:243-247`, `app/actions.go:344-376`). Note `validateLimits` (`config.go:245-247`) already verifies `content_attempt_window <= retention.audit_events` under the assumption that `audit_events` retention prunes windowed attempts, yet `pruneAttempts` was never updated to do so.
- **Suggested fix:** Pass `ContentAttemptWindow` into `store.Retention`. When `ContentAttemptWindow > 0`, prune `attempts:%` rows older than `max(AuditEvents, ContentAttemptWindow)` (keeping the `max(r.at)` guard only when `ContentAttemptWindow == 0`). In `AttemptSummaries`, filter by window in SQL when windowed rather than loading up to 500 historical rows.

##### M8 — `VersionSupport` / `LineOf` accepts malformed and pre-release versions and gives a false opt-in hint for unknown versions
- **Location:** `internal/action/compat.go:42-99,146-147,164-177`
- **Defect:**
  1. **False opt-in hint (`compat.go:173-177`):** When a version is unknown (`!known`), `VersionSupport` appends `"Set [automation] untested_versions = \"act\" to allow writes to versions outside the tested lines"`, even though line 165 requires `known` and `untested_versions = "act"` still refuses unknown versions.

##### M9 — Migration 0020 backfill SQL mishandles `"action #N"` without a trailing space and backdates custom non-24h cooldowns on fallback
- **Location:** `internal/store/migrations/0020_cooldown_since.sql:9-15`
- **Defect:**
  1. Line 12 computes `substr(reason, 9, instr(substr(reason, 9), ' ') - 1)`. For the current format `"action #45 (no_progress_recovery)"` this yields `"45"`. If a reason is `"action #45"` (no space), `instr(...)` is `0`, `0 - 1 = -1`, and in SQLite `substr(X, 9, -1)` returns the character *preceding* index 9 (`'#'`), so `CAST('#' AS INTEGER)` is `0` and the lookup fails.
  2. Line 15 falls back to `until - 86400000` (assuming 24h) whenever `since IS NULL` (e.g., if the action intent was already pruned or the reason didn't match). If an operator had configured `success_cooldown = "6h"` prior to schema 20, `until - 24h` places `since` 18 hours *before* the action occurred, causing `ActiveCooldowns` with a 1h cooldown to expire it immediately even 1 minute after the action.
- **Concrete failure scenario:** An installation running `success_cooldown = "6h"` with a pruned or non-standard cooldown reason upgrades from v19 to v20; the cooldown's `since` is backfilled to `T - 18h`, immediately expiring the active cooldown.
- **How verified:** Code path traced and SQLite `substr` negative-length semantics verified (`0020_cooldown_since.sql:9-15`, `action.go:515`).
- **Suggested fix:** Per `AGENTS.md`, **do not edit committed migration 0020**. Current production code always writes `"action #%d (%s)"` (`action.go:515`), so real v19 rows with unpruned intents match cleanly; document the fallback assumption in upgrade notes and ensure future SQLite string-parsing migrations handle absent delimiters (e.g. `instr(substr(...) || ' ', ' ') - 1`).

##### M10 — Excessive per-cycle log volume and redundant per-torrent SQLite `UPDATE`s on shared hosts
- **Location:** `cmd/housekeeparr/main.go:286-291`, `internal/engine/cycle.go:306-317`
- **Defect:**
  1. **Log spam (`main.go:286-291`):** Every 10-minute cycle logs one `INFO` line for *every* candidate finding in `r.Evaluations` and one `WARN` line for *every* open breaker in `r.Breakers`, even when nothing changed. On eclipse (~72 open findings), that produces ~10,400 `INFO` lines/day plus 144 `WARN` lines/day per held breaker.
  2. **Redundant SQLite writes (`engine/cycle.go:306-317`):** Every cycle executes `tx.RefreshRetained(...)` (`UPDATE retained_transfers ...`) once for *every* transfer in every client listing (587 `UPDATE`s/cycle on eclipse; 4,000 `UPDATE`s/cycle in the reference workload), even when `retained_transfers` has 0 or only a handful of rows.
- **Concrete failure scenario:** On a shared seedbox with bounded journald/log space or shared spinning disk I/O, repetitive per-cycle INFO/WARN spam floods logs and hides actual dispatches/errors, while hundreds of no-op `UPDATE` statements run inside the write transaction every cycle.
- **How verified:** Code path traced (`main.go:286-291`, `cycle.go:306-317`, `store/retained.go:74-81`).
- **Suggested fix:** Log `INFO` only when an evaluation dispatches, fails, or changes result since the prior cycle (emit one concise cycle summary at `INFO`, per-finding unchanged details at `DEBUG`). Log breaker `WARN` on open/close transitions (and optionally once daily). In `cycle.go`, query the small active `retained_transfers` set once before the loop and call `RefreshRetained` only for transfers actually present in it.

### 2.2 Plausible / Conditional Findings

These are not confirmed bugs under today's adapters/config, but represent realistic failure modes or design trade-offs that warrant explicit decisions or hardening:

##### P1 (Medium, plausible) — Near-complete 4h progress window can keep `working[c] > 0` for hours after a VPN outage
- **Location:** `internal/app/dispatch.go:436`
- **Concern:** `progressed := a != nil && a.Status != policy.StatusQualified && a.LastProgressAt != nil && a.Window > 0 && now.Sub(*a.LastProgressAt) <= a.Window`. If a single near-complete transfer (≥95%, `a.Window = 4h`) made 1 byte of verified progress 10 minutes before the client's VPN dropped, `progressed` stays `true` for 3h 50m after the VPN dies. Every other download hits its 60m metadata or 90m no-progress window and gets recovered against the dead VPN because `working[c]` stays `1`.
- **How verified:** Code path traced (`dispatch.go:436`, `policy/policy.go:42-43`).
- **Suggested fix:** Evaluate whether client-liveness `progressed` should require progress within a bounded recent horizon (e.g., `min(a.Window, max(2*pollInterval, 30m))`) rather than up to 4 hours, since an active healthy network should show either peers or recent progress within ~30–60 minutes.

##### P2 (Medium, plausible) — Correlated-stall `inContact` depends on peer-count semantics and omits `UploadRate`
- **Location:** `internal/store/transfers.go:484-489`
- **Concern:** For seeding/complete transfers, `DownloadRate` is always 0, so `inContact` depends entirely on `ConnectedPeers > 0 || ConnectedSeeds > 0`. All four current adapters populate `ConnectedPeers` for seeding leechers (`peersConnected`, `num_leechs`, `num_peers`, `d.peers_connected`). However: (a) if a client version counts local/LAN/half-open peers during an upstream VPN outage, `complete_contact` stays non-zero (false negative); (b) if a future adapter reports upload traffic without peer counts, `inContact` misses it (false positive).
- **How verified:** Code path traced across all 4 client adapters and `store/transfers.go:484-489`.
- **Suggested fix:** Document the adapter contract requirement for `ConnectedPeers` on complete transfers; consider also capturing `UploadRate` if a future client lacks peer counts on complete transfers.

##### P3 (Low, plausible) — `RetainedUsage` infers `NoPayload` implicitly from `wanted_bytes IS NULL AND verified_bytes = 0`
- **Location:** `internal/store/retained.go:155-156`, `internal/action/action.go:818-823`
- **Concern:** Currently all four adapters report `WantedBytes` whenever `VerifiedBytes` is known, so `wanted_bytes IS NULL && verified_bytes = 0 && disposition = 'stopped'` matches only stopped metadata magnets. If any future adapter or fixture reports `VerifiedBytes = 0` with `WantedBytes = Unknown` for a stopped non-metadata transfer, `RetainedUsage` would misclassify it as `NoPayload` instead of `UnknownSize`, bypassing a configured `retained_gib` byte ceiling.
- **How verified:** Code path traced across all 4 adapters, `action.go:809-825`, and `store/retained.go:152-159`.
- **Suggested fix:** Store an explicit `no_payload` flag (or `origin_state`) in `retained_transfers` when a future migration touches that table.

##### P4 (Low, operational) — Repeated-refusal breaker (`refusals_to_open = 2` in `24h`) can over-trip on benign queue races
- **Location:** `internal/app/dispatch.go:343-377`, `internal/config/config.go:658-661`
- **Concern:** `actionBreakers` opens a 24-hour manager breaker after 2 `IntentFailed` automatic actions in 24h. Because `404 Not Found` on `DELETE /api/v3/queue/{id}` is classified as `ErrPermanent` (`IntentFailed`), two unrelated benign races over a 24-hour period (where Sonarr removed or updated a queue item in the milliseconds between the live check and `DELETE`) will halt all automatic recovery and proactive searches on that manager for up to 24 hours.
- **How verified:** Code path traced (`dispatch.go:343-377`, `action/action.go:433-444`, `action/action_test.go:426-434`).
- **Suggested fix:** Either distinguish auth/config refusals (`ErrUnauthorized`, `ErrUnsupported`, 400/403) from single-item 404/409 races, or shorten `refusal_window` / require consecutive refusals so isolated 404 races do not pause an entire manager for 24h (per SPEC §5 anti-timidity rule).

## 5. Operational Fitness for Shared Hosts

Evaluated against a typical shared seedbox profile (Ultra.cc eclipse: ~600 torrents, 400+ missing items, 10-minute poll, unprivileged user systemd service, shared disk/RAM):

- **Memory & CPU:** Strong. Observed 12–40 MB RSS (peak 54 MB) and ~22 s CPU over 3 hours on eclipse (`STATUS.md:27,83`). Single static Go binary with embedded SQLite and zero Node/broker overhead fits SPEC §1 & §2.2 well.
- **Log volume (defect — M10):** Unbounded per-cycle `INFO` evaluation lines (~10k lines/day for 72 findings) and per-cycle `WARN` breaker lines (144 lines/day/breaker) are noisy on shared hosts with tight user-journal limits. Needs transition-based logging and cycle summaries.
- **SQLite I/O & storage growth (defects — H5, M10):**
  - `SaveTransferSnapshot` smartly skips `transfer_observations` inserts for unchanged complete transfers (`transfers.go:143-146`), keeping WAL churn low for seeding torrents.
  - However, `engine/cycle.go:306-317` undoes some of that thrift by running `UPDATE retained_transfers` for every single torrent every cycle (**M10**), and `action_attempts` grows without pruning under default windowed attempts (**H5**).
  - `Store.Open` configures WAL + `busy_timeout`, which is appropriate for single-writer local disk (not NFS, per SPEC §10).
- **Polling load & outage behaviour:**
  - Bounded `MaxConcurrency` (default 4, configurable to 2 on shared hosts), per-connection timeouts (`30s`), jitter (`30s`), paginated queue reads (`200 × 25`), capped supplemental tracker reads (`25`), and rotating hourly missing-content sweeps (`500/manager`) are well-behaved.
  - **When a manager is down:** Findings whose client shares that manager (per `ManagersFor`) correctly wait (`fresh[m] == false`), while unrelated healthy managers continue. Existing findings stay open with stale markers instead of falsely resolving.
  - **When a client is down:** Transfers are not marked gone; no candidates for that client enter dispatch. However, **M1** currently still evaluates `breakers()` on the stale client and logs `WARN automation held` every cycle.
  - **CLI while daemon runs:** Still exits 3 on writer lock contention for `ack`/`snooze`/`act`/`review`/`pause` (known remaining v1 item, `STATUS.md:662`). On headless shared hosts, operators must use the web UI or temporarily stop the service for `review`/`restore-ack`.

### 6.4 Concrete Acceptance Criteria for the Top 3 Proposed Areas

#### Top 1 — Area 1: Release-source reliability
1. **Data join & provenance:** Joins manager grab/import/failed history (`indexer`, `releaseGroup`, `downloadId`) with Housekeeparr's persisted stall diagnoses and recovery outcomes over a configurable rolling window (default 14 days), scoped per manager. Grabs lacking an identifiable indexer or release group are counted as `unknown`, never silently dropped or merged.
2. **Bounded I/O:** Uses incremental/cursor-based history paging (not full history re-scans every 10-minute cycle), bounded per cycle, with persisted aggregates in SQLite pruned by existing audit retention.
3. **Finding precision & non-timidity:** Opens one deduplicated `notice`/`warning` finding per `(manager, indexer)` only when both sample size (`>= 30` grabs, configurable) and failure threshold (`< 50%` imported, configurable) are met, excluding grabs still actively downloading within grace/settling windows. Never blocks recovery or edits manager settings.
4. **Actionable explanation:** Finding, `Sources` web page (under `base_path`), and `housekeeparr sources [--json]` show grabs, imports, stalls, failures, still-active, and import rate, plus concrete manager-side actions (minimum seeders, indexer priority, tags). Recovery finding explanations optionally include the source's recent failure rate when known.
5. **Sanitization & tests:** Indexer names/diagnostics never leak passkeys or tracker URLs; deterministic tests verify incremental paging, in-flight grab exclusion, threshold hysteresis/resolution, and CLI/web parity.

#### Top 2 — Area 4 + Area 7: Import-pipeline stalls & tracker-blacklisted-client diagnosis
1. **Complete-but-errored torrent diagnosis:** When a transfer has `VerifiedBytes == WantedBytes` (known, > 0), `StateClass == StateError` (or tracker error stopping it), and a present manager queue item still tracking it as downloading, Housekeeparr opens a specific finding explaining that the payload is complete and recommending manual import / client inspection — never proposing stall recovery or blocklisting.
2. **Tracker-blacklisted-client classification (Area 7):** `domain.ClassifyTrackerError` classifies recognised client-ban phrases (sanitized, fixture-tested across Transmission/Deluge/qBittorrent/rTorrent) as a distinct non-recovery source cause (`source_client_rejected`), opening a finding naming the client version and tested lines (from `action.Lines`) and explicitly *not* qualifying for `preserved_data_failure` recovery.
3. **Needs-extraction & sample-only diagnosis:** For import-pending queue rows settled past `import_settle`, reads the client file list *only* for those specific transfers (bounded per cycle, graceful `unknown` when unsupported). Reports `needs_extraction` only on positive evidence of archive files (`.rar`, `.r00`, `.zip`, `.7z`) with no non-sample video file; reports `sample_only` only when video file(s) exist and manager/file evidence positively identifies sample-only content. Missing file-list capability produces explicit uncertainty, never a guessed cause.
4. **Safety & tests:** Zero write operations added; contract tests with sanitized fixtures for each client's file-list and tracker-error format; negative tests confirming active downloads or mixed archive+video folders do not false-positive.

#### Top 3 — Area 2: Per-series / library coverage view
1. **Bounded collection:** Reads series/movie totals on the hourly missing sweep cadence (never on page load and never on the 10-minute transfer poll), with bounded pagination and persisted per-series/per-movie summaries in SQLite.
2. **Evidence-backed gap states:** Each missing monitored aired item is classified into exactly one evidence-backed state: `never_searched`, `searched_no_grab` (with last search & next retry), `grabbed_downloading`, `grabbed_stalled` (with recovery attempt count), or `import_pending` — never guessing "no release exists" from zero grabs.
3. **Coverage trend:** Records a compact daily coverage snapshot per manager (monitored aired total, present count, missing count) retained under `audit_events` retention so operators can see whether tuning/recovery improved completeness over days/weeks.
4. **CLI/web parity & shared-host performance:** Served via a shared `app.Service` method powering both `/coverage` (honoring `base_path`, CSP, and auth) and `housekeeparr coverage [--json]`. Page render executes local SQLite reads only (<50 ms on 1,500 episodes) with zero upstream API calls.
