`old_download_id`. `internal/app/dispatch.go:330` uses that map to exclude
transfers from both correlated-stall counts, without client identity.
`internal/app/actions.go:124` also uses it for the already-recovered explanation.
SPEC §3.1 defines physical identity as client instance plus native identity.

Reproduced using the existing deterministic application world: recover hash A
on qbit/Sonarr, then put hashes A, B and C in a qualified stall on qbit2, with

and **one Radarr failure/blocklist request is sent**. This is a safeguard
failure, not merely incorrect explanation text.

Key handled-transfer evidence by client plus native identity, and relate it to
the actual handled association/attempt. Recover client identity from durable
intent evidence or add a forward migration if necessary. Old ambiguous records
must not suppress a breaker. Cover cross-client hash reuse, a new association
for a previously recovered hash, restart, and the intended kept-running case.
The latter two are requested follow-up tests, not additional reproduced defects.

## R12 — high: keep-running recovery bypasses an existing capacity ceiling

`internal/action/plan.go:349–363` checks retained capacity only inside `if stop`.
A private/unknown-privacy keep-running recovery therefore requests replacement
even when the existing retained count is already at its ceiling. A planner
reproduction at the default count limit finds no capacity prerequisite at all.
The private-mode test currently explicitly expects its absence.

SPEC §7.1 says ceilings stop new affected replacements/acquisitions. Whether a
running orphan itself should increment retained usage is a separate accounting
decision; it does not justify bypassing an already exhausted ceiling. Separate
current-capacity gating from the incremental cost of this action. Test count,
bytes, unknown size, exact boundaries and private/unknown-privacy variants.
Keep the user-authorized leave-running default.

## Specification corrections before the next write workflow

These are recommendations, not newly approved numeric defaults or scope changes.

1. **Reconcile §6 with §7 step 4.** The approved keep-running default knowingly
   retains an active slot; §6's final sentence and §7's slot-release requirement
   still read as unconditional. Make the explicit keep-running exception clear,
   including ongoing bandwidth/storage, later completion, and import ambiguity.
   The real tests establish continued registration and activity, not what happens
   when the old release later completes. Add a focused real-instance completion
   probe before claiming that lifecycle is understood; do not silently stop it.
2. **Define retained accounting (§7.1).** Recommend tracking all transfers left
   behind by recovery, distinguishing stopped from deliberately running, and
   keeping acquisition limits independent of the stop operation. Current records
   only describe stopped transfers. Specify whether the byte budget measures
   logical wanted size or known downloaded payload; these differ. In particular,
   `retainedSize` returns zero for metadata state and `recordRetained` stores zero
   as wanted bytes when size is unknown. Zero currently downloaded payload is not
   a known zero logical size. Define freshness/update behavior if an operator
   resumes a stopped magnet and it obtains metadata or downloads. The engine
   presently releases retained records on authoritative disappearance but does
   not refresh their sizes. Do not convert unknown logical size into zero.
3. **Give preserved-data failure handling a concrete contract.** It appears in
   the compatibility matrix and implementation plan, but lacks a dedicated
   evidence/permission/effect/outcome specification. Define qualifying causes,
   fresh corroboration, local disk/permission/outage exclusions, import ambiguity,
   allowed manager/client steps, privacy, and refusal/reconciliation outcomes.
   Existing real-instance evidence disproves equating complete with files present
   or stale error text with an actionable failed release. Do not require recursive
   filesystem inspection or implement automatic rechecks implicitly. Start with
   a narrowly evidenced case; unsupported causes remain visible and held.
4. **Bound the metadata exception accurately.** Keep the approved unknown-privacy
   metadata behavior. Explain it as a scoped policy choice with supported,
   freshly revalidated metadata evidence; the API does not establish tracker
   obligations. Remove universal claims such as “forfeits nothing” and “no ratio
   obligation” from previews/spec rationale. Distinguish absent metadata, unknown
   privacy and unknown logical size rather than making one erase the others.
5. **Specify correlated-stall populations.** State the scope, numerator and
   denominator, freshness, metadata inclusion, and precise handled-attempt
   exclusion. Metadata inclusion is reasonable; hash-global lifetime exclusion
   is not. Keep timing/threshold numbers labeled proposals. Add the missing
   positive-piece-unavailability policy to diagnostic revision hashing; this is
   already required by §13.4, not a reason to redesign the diagnosis engine.

Also refresh the SPEC opening (metadata recovery now exists), stale STATUS
planner text (“known-public” and unconditional stop), and old remaining-work
wording. Keep evidence levels distinct. Resolve pause/manual semantics in a
small explicit matrix when touching those controls, not as a global blocker.
